## Goal

Run the production images and a one-off migrate container on your Mac before any server is
involved. If it works here, the server only adds a domain and real secrets; if it breaks here,
you find out in seconds instead of during a deploy. CI will run this same file to smoke-test
every pull request (lesson 5.2).

## Steps

- **Startup order** comes from `depends_on` conditions: Postgres must be *healthy*, then
  `migrate` must *exit with 0*, and only then does the app start. A failed migration leaves
  the old data untouched and the new app never starts.
- **`migrate` uses the app's image** with a different `command`. The image is built once
  (`build:` on both services names the same image).
- **The app's healthcheck** calls `/api/health`, which answers 503 when the database is down,
  so "healthy" means "can serve requests", not just "process is running". `start_interval`
  checks every 2 s while it starts, then every 30 s, to keep the logs quiet.
- **`x-…-env` and `&` / `*`** are YAML anchors: one block of environment variables, used by
  both containers.
- **Throwaway values, written inline.** The password is `guestbook` and that is fine: nothing
  here is reachable from outside your computer. Lesson 2.3 covers where real values live.
- **Port 8080, on `127.0.0.1` only**: the port the server's Caddy listens on, and only your
  computer can reach it.

```bash
cd examples/react-hono-postgres
(cd frontend && npm run build)

```

</TabItem>
<TabItem label="Next.js">


`--build` rebuilds the image if the code changed; `--wait` returns once every service is
healthy (or has exited successfully), and fails if one isn't.

The logs are the JSON lines the server will produce, with `"env":"production"`:

```bash
docker compose logs migrate --no-log-prefix
```

```json
{"level":30,"time":"…","track":"…","env":"production","version":"local","msg":"migrations applied"}
```

Running the migrations again is safe; Drizzle skips the ones already recorded:

```bash
docker compose run --rm migrate
```

It logs `migrations applied` again and changes nothing.

Finally, stop the database and watch the health check notice:

```bash
docker compose stop postgres
curl -s -w ' %{http_code}\n' localhost:8080/api/health
docker compose up -d --wait postgres
curl -s -w ' %{http_code}\n' localhost:8080/api/health
```

```
{"ok":false,"db":"down",…} 503
{"ok":true,"db":"up",…} 200
```

The app survives a database restart and reconnects on its own. This 503 is what the uptime
monitor will alert on in Part 6.

## What you learned

Production is a set of images plus configuration, started in a fixed order: database, then
migrations, then app. Running that on your computer first turns most deploy failures into
local ones.

## Undo

```bash
docker compose down      # stop and remove the containers, keep the data
docker compose down -v   # also delete this stack's database volume
```

Only one track can use port 8080 at a time: `down` one before starting the other.
