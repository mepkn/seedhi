## Goal

One Zod schema checks input in the form and again on the server, which answers `400` with
a message per field.

The `POST` handler (lesson 1.4) runs the same `NewEntry.safeParse` and throws a

### 1. The contract

<Code code={contractTop} lang="ts" title="src/lib/contract.ts (start)" />

The same file as in the other track. It imports nothing server-only, so the form, a

### 2. Validate in the form

<Code code={nextSubmit} lang="tsx" title="src/components/EntryForm.tsx (submit)" />

The form checks with `NewEntry` before calling the Server Action, and shows the server's
per-field messages if the server disagrees. The action returns its error in the standard
shape (lesson 1.6) instead of throwing.

### 3. Validate again on the server

`createEntry` in `src/lib/entries.ts` (lesson 1.4) runs `NewEntry.safeParse` and throws a
`VALIDATION_FAILED` error with `fieldErrors(...)`. A Server Action is a public `POST`
endpoint like any other, so anyone can call it without your form: both it and
`POST /api/entries` go through `createEntry`, so neither trusts its input.

## Verify

Skip the form and send bad input straight to the API:

```bash
curl -s -X POST localhost:3000/api/entries \
  -H 'content-type: application/json' \
  -d "{\"name\":\"\",\"message\":\"$(printf 'x%.0s' {1..300})\"}" | jq
```

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Check the highlighted fields.",
    "requestId": "c5322c52-61eb-4a36-be5e-b49ef7d0d68d",
    "fields": {
      "name": "Name is required",
      "message": "Message must be at most 280 characters"
    }
  }
}
```

In the browser (lesson 1.8), submit the empty form: both fields show their message and no
request appears in the Network tab.

## What you learned

Validate in the browser for a quick answer, on the server for safety, and use one schema
for both so the rules can't drift. The database column limits come from the same constants.
